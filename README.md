# dup_stat

Поиск файлов-дубликатов в директории по хешсумме содержимого и (опционально)
дополнительным атрибутам файла — имени и размеру. Дополнительно (включено по
умолчанию) находит директории, которые являются **полными** дубликатами друг
друга — совпадает вся рекурсивная структура и содержимое.

## Установка (виртуальное окружение)

Сам пакет не имеет внешних зависимостей (только стандартная библиотека,
Python >= 3.8), но для интерактивной работы рекомендуется venv:

```bash
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

pip install --upgrade pip
pip install -e .                 # ставит сам dup_stat (даёт команду dup-stat)
pip install -r requirements.txt  # jupyter/pandas/openpyxl/matplotlib — ноутбук и Excel-экспорт
```

## Использование

```bash
python -m dup_stat /path/to/directory
```

Полезные флаги:

| Флаг | Назначение | По умолчанию |
|---|---|---|
| `--algorithm` | алгоритм хеширования (`sha256`, `sha1`, `md5`, `blake2b`, ...) | `sha256` |
| `--match` | критерий совпадения дубликатов: `hash`, `hash+name`, `hash+name+size` | `hash` |
| `--min-size` | игнорировать файлы меньше N байт | `0` |
| `--follow-symlinks` | переходить по симлинкам | выключено |
| `--format` | формат отчёта: `text` или `json` | `text` |
| `--chunk-size` | размер блока чтения файла при хешировании | `1048576` |
| `--workers` | число потоков для параллельного хеширования; `1` — отключить параллелизм | авто |
| `--partial-hash-bytes` | размер префикса для предварительного хеша (отсев без чтения файла целиком); `0` — отключить | `65536` |
| `--no-dirs` | не искать директории-полные-дубликаты | включено |
| `--no-progress` | не показывать индикатор прогресса при хешировании | показывается, если вывод в терминал |
| `--save-dir` | дополнительно сохранить результаты локально в директорию (SQLite + JSON + pandas.DataFrame + Excel) | не сохранять |
| `--append-timestamp` | добавить результаты этого запуска к уже сохранённым по указанному timestamp (требует `--save-dir`) | не добавлять |

Примеры:

```bash
# Только по содержимому (классические дубликаты, независимо от имени файла)
python -m dup_stat ~/Downloads

# Файл считается дубликатом только если совпадают и содержимое, и имя
python -m dup_stat ~/Downloads --match hash+name

# JSON-отчёт для дальнейшей обработки
python -m dup_stat ~/Downloads --format json > report.json

# Сохранить результаты локально: SQLite + JSON + pandas.DataFrame + Excel, одинаковый timestamp
python -m dup_stat ~/Downloads --save-dir ./results

# Не искать директории-дубликаты, только файлы (старое поведение)
python -m dup_stat ~/Downloads --no-dirs

# Добавить результаты нового прогона к уже сохранённым (по timestamp)
python -m dup_stat ~/Downloads --save-dir ./results --append-timestamp 20260823_084610
```

Если пакет установлен (`pip install -e .`), доступна команда `dup-stat`
как эквивалент `python -m dup_stat`.

## Как это работает

Поиск дубликатов идёт в три стадии, каждая следующая обрабатывает
только кандидатов, прошедших предыдущую — это ключевая оптимизация
скорости, подробнее в разделе "Производительность" ниже:

1. `RecursiveFileScanner` рекурсивно обходит директорию и отбирает файлы.
2. **Стадия 1 (размер).** Файлы группируются по размеру; файлы с
   уникальным размером сразу отбрасываются — они физически не могут
   иметь одинаковое содержимое, хешировать их не нужно.
3. **Стадия 2 (частичный хеш).** Для оставшихся кандидатов считается
   хеш только первых `--partial-hash-bytes` байт (по умолчанию 64 КБ).
   Разные файлы почти всегда отличаются уже в начале, так что это
   отсеивает "случайных соседей по размеру" без чтения файла целиком.
4. **Стадия 3 (полный хеш).** `HashlibFileHasher` считает хешсумму всего
   файла (по умолчанию SHA-256) только для того, что осталось после
   стадий 1-2 — то есть для реальных кандидатов в дубликаты. Хеширование
   на стадиях 2 и 3 выполняется в пуле потоков (`--workers`).
5. `DuplicateKeyStrategy` строит ключ группировки — по умолчанию это
   просто хеш, но можно потребовать совпадения ещё и имени и/или размера.
6. Файлы с одинаковым ключом объединяются в `DuplicateGroup`.
7. Если не указан `--no-dirs`, `DirectoryDuplicateFinder` дополнительно
   ищет директории-полные-дубликаты (см. раздел ниже), а файловые группы,
   целиком покрытые найденной директорией, убираются из вывода —
   иначе один и тот же дубликат считался бы дважды.
8. Итоговый список групп (файлов и директорий вместе) всегда отсортирован
   по размеру копии **по убыванию** (`sort_groups_by_size_desc`) — это
   единственная точка сортировки, поэтому и текстовый/JSON-вывод, и
   сохранённые SQLite/DataFrame всегда идут в одном и том же порядке.
9. `ReportFormatter` (текстовый или JSON) выводит найденные группы,
   помечая для каждой тип записи — `файл` или `директория` (поле `kind`),
   и суммарный размер "лишних" копий (`wasted_size`) — то есть сколько
   места освободится, если в каждой группе оставить только одну копию.
10. Если указан `--save-dir`, `ResultPersistence` дополнительно сохраняет
    результаты локально (см. раздел ниже), в том же порядке.

## Директории-дубликаты

По умолчанию (без `--no-dirs`) `dup_stat` ищет не только отдельные
файлы-дубликаты, но и **директории**, которые являются полными
дубликатами друг друга — то есть у них совпадает вся рекурсивная
структура (имена и вложенность файлов и поддиректорий) и содержимое
каждого файла:

```
[1] тип: директория, 2 копий, размер каждой: 97.66 KB, хеш: 768b54e3...
      - /home/user/photos_2023
      - /home/user/photos_backup
```

Ключевая особенность — это не стоит ни одного лишнего чтения файла с
диска. `DirectoryDuplicateFinder` (`directory_finder.py`) целиком
переиспользует то, что уже посчитал `DuplicateFinder` для поиска
файловых дубликатов (полные хеши файлов, у которых есть хотя бы один
"близнец" где-то в дереве). Это корректно благодаря простому факту:
любой файл, реально входящий в пару директорий-дубликатов, обязан
иметь точный "близнец" по содержимому в парной директории — а значит,
он уже гарантированно попал на все три стадии файлового пайплайна
(размер → частичный хеш → полный хеш) и уже хеширован. Файл без
"близнеца" (глобально уникальный размер) не может быть частью
дубликата-директории в принципе — такая директория и все её родители
отсекаются без построения сигнатуры.

Сигнатура директории строится снизу вверх, как в Merkle-дереве: хеш
директории — это хеш отсортированного списка (имя, тип, хеш) всех её
прямых потомков, где для вложенных поддиректорий используется уже
посчитанная сигнатура. Совпадающая сигнатура гарантирует побайтовое
совпадение всего содержимого рекурсивно.

Показываются только "верхние" пары дубликатов — если директория A
дублирует директорию B, их общая вложенная поддиректория не
показывается отдельной строкой (`_drop_nested_duplicates`), а файловые
группы, целиком лежащие внутри A/B, убираются из отчёта
(`filter_subsumed_file_groups`) — иначе один и тот же физический
дубликат считался бы дважды и в отчёте, и в сумме "лишнего" места.

## Производительность

Три оптимизации, дающие основной выигрыш по скорости на больших
директориях (проверено на синтетическом тесте: 400 файлов по 2 МБ,
~800 МБ суммарно — время поиска дубликатов сократилось с ~2.6 с до
~0.36 с, результат идентичен):

- **Трёхстадийная фильтрация** (размер → частичный хеш → полный хеш,
  см. `finder.py`) — самый дорогой шаг, полное чтение файла, выполняется
  только для файлов, которые уже прошли два дешёвых фильтра. Особенно
  заметно на директориях с большим количеством больших файлов
  одинакового размера, но разным содержимым.
- **Параллельное хеширование** (`hash_computation.py`,
  `ThreadPoolHashComputation`) — чтение и хеширование файлов идёт в
  пуле потоков: это I/O-bound работа, а hashlib к тому же освобождает
  GIL на крупных чанках, поэтому несколько файлов реально обрабатываются
  одновременно. `--workers 1` отключает параллелизм.
- **Более быстрый обход директории** (`scanning.py`) — через
  `os.scandir` вместо `Path.rglob`: тип записи (файл/директория/симлинк)
  берётся из уже прочитанного `DirEntry` без лишнего syscall, а
  `stat()` на размер файла выполняется только если задан `--min-size`
  (в дефолтном случае вообще не делается лишних системных вызовов).

Всё это — реализации абстракций (`HashComputationStrategy`,
`FileScanner`), поэтому способ ускорения можно менять или расширять, не
трогая логику самого поиска дубликатов (Open/Closed).

## Индикатор прогресса

При запуске в терминале во время хеширования показывается крутящееся
колёсико, проценты и счётчик "N из M файлов":

```
\ полный хеш:  63% (312/495)
```

Общее количество файлов на каждой стадии уже известно заранее (это
результат фильтрации на предыдущих стадиях, см. "Как это работает"
выше), поэтому проценты считаются точно, без догадок. Индикатор
показывается отдельно для стадии предварительного хеша и для стадии
полного хеша (см. "Производительность") — они по-разному называются в
строке прогресса, чтобы было понятно, какая часть работы идёт сейчас.

Отключить: `--no-progress`. Автоматически не показывается, если вывод
перенаправлен в файл или пайп (`> report.txt`, `| less`) — индикатор
пишет управляющий символ `\r` для перерисовки строки, который в файле
выглядел бы как мусор, так что при отсутствии терминала он молча
отключается сам.

Реализация — в `dup_stat/progress.py`: `ProgressReporter` — абстракция
(OCP/DIP, как и везде в проекте), `NullProgressReporter` — "ничего не
делать" (по умолчанию при программном использовании пакета и в
тестах), `SpinnerProgressReporter` — реализация для CLI. Подключается
через `ThreadPoolHashComputation(progress=...)` — сам `DuplicateFinder`
ничего не знает про индикатор прогресса.

## Сохранение результатов локально (`--save-dir`)

Флаг `--save-dir DIR` сохраняет результаты сразу в **четырёх**
локальных файлах — SQLite, JSON, `pandas.DataFrame` и Excel — с
**одним и тем же timestamp** в имени, чтобы файлы одного запуска было
легко сопоставить друг с другом:

```
DIR/dup_stat_results_20260823_052141.sqlite3
DIR/dup_stat_results_20260823_052141.json
DIR/dup_stat_results_20260823_052141.pkl
DIR/dup_stat_results_20260823_052141.xlsx
```

Во всех форматах — одна и та же плоская таблица: `group_id, kind,
file_hash, path, name, size_bytes, mtime, wasted_bytes`, одна строка
на файл или директорию (`kind` = `file` / `directory`).

- **`.sqlite3`** — не требует сервера, хранит всё в одном файле,
  позволяет делать SQL-запросы. Открыть можно любым SQLite-клиентом
  или `sqlite3` из stdlib:

  ```python
  import sqlite3
  conn = sqlite3.connect("dup_stat_results_20260823_052141.sqlite3")
  conn.execute("SELECT * FROM duplicate_entries WHERE kind = 'directory'").fetchall()
  ```

- **`.json`** — та же таблица в виде JSON-массива объектов, без
  зависимости от pandas — удобно для скриптов на любом языке:

  ```python
  import json
  rows = json.load(open("dup_stat_results_20260823_052141.json", encoding="utf-8"))
  ```

- **`.pkl`** — сохранён как `pandas.DataFrame` через `to_pickle`
  (сохраняет типы колонок в отличие от CSV). Загружается одной командой:

  ```python
  import pandas as pd
  df = pd.read_pickle("dup_stat_results_20260823_052141.pkl")
  ```

- **`.xlsx`** — та же таблица, открывается в Excel/LibreOffice/Google
  Sheets, либо через pandas: `pd.read_excel("dup_stat_results_20260823_052141.xlsx")`.

`.sqlite3` и `.json` не требуют внешних зависимостей (stdlib). Для
`.pkl` и `.xlsx` нужны `pandas` (оба формата) и дополнительно
`openpyxl` (только для `.xlsx`) — если одного из пакетов нет,
соответствующий формат просто пропускается с понятным сообщением в
консоли ("Пропущено: ..."), а остальные форматы всё равно сохраняются.

Реализация — в `dup_stat/storage.py`: `ResultExporter` — абстракция
экспортёра (OCP: новый формат, например CSV или Parquet, добавляется
новым классом), `SqliteResultExporter` / `JsonResultExporter` /
`DataFrameResultExporter` / `ExcelResultExporter` — её реализации
(`_build_dataframe()` переиспользуется двумя последними, чтобы не
строить `DataFrame` дважды — DRY). `ResultPersistence` генерирует
общий timestamp, прогоняет через него все переданные экспортёры и
возвращает `PersistenceResult(saved=[...], skipped=[...])` — какие
файлы реально сохранены, а какие форматы пришлось пропустить и почему.

## Накопление результатов между запусками (`--append-timestamp`)

По умолчанию каждый запуск с `--save-dir` — независимый снимок: новый
timestamp, новый набор файлов. Флаг `--append-timestamp TIMESTAMP`
позволяет вместо этого **добавить** результаты текущего запуска к уже
сохранённым (по timestamp прежнего сохранения), не теряя историю:

```bash
# Первый прогон — обычное сохранение
python -m dup_stat ~/Downloads --save-dir ./results
# ... появился, например, dup_stat_results_20260823_084610.json

# Позже: новый скан, результаты добавляются к прежним
python -m dup_stat ~/Downloads --save-dir ./results \
    --append-timestamp 20260823_084610
# ... старые файлы (..._084610.*) остаются как были,
#     появляется НОВЫЙ набор файлов с НОВЫМ timestamp,
#     содержащий объединённые и заново отсортированные данные.
```

Как это работает (`dup_stat/result_merge.py`):

1. `load_previous_rows()` читает прежний `..._<TIMESTAMP>.json` (именно
   JSON — единственный формат, который не требует pandas для чтения).
2. `merge_with_previous()` объединяет старые записи с только что
   найденными группами и **пересобирает группы дубликатов заново** —
   по паре (тип записи, хеш), а не просто складывает старые и новые
   строки в одну таблицу. Так, если новый скан нашёл третью копию уже
   известного дубликата, она попадёт в ту же группу, а не в отдельную.
3. Если один и тот же путь встречается и в старых, и в новых данных
   (например, при повторном сканировании той же директории) — в
   объединённом результате остаётся более свежая запись, а не устаревшая.
4. Группа, которую новый скан не затронул (её файлов не было в текущей
   директории сканирования), сохраняется как есть — история не
   теряется, даже если сканировать в следующий раз уже другую директорию.
5. Итог пересортировывается по размеру, как и всегда (`sort_groups_by_size_desc`),
   и сохраняется под новым timestamp — этот же объединённый набор идёт
   и в консольный отчёт, и во все форматы `--save-dir`.

Старые файлы результата (`..._<TIMESTAMP>.*`) при этом не открываются
на запись и не удаляются — слияние только читает один из них (JSON).
Требует `--save-dir` (без него `--append-timestamp` — ошибка, так как
непонятно, откуда брать прежние результаты).

## Архитектура и принципы SOLID / DRY

Код разбит на модули по зоне ответственности (Single Responsibility):

- `models.py` — данные: `FileRecord` (используется и для файлов, и для директорий — одна структура, DRY), `DuplicateGroup` (с полем `kind: EntryKind`), `FileScanResult`, общий помощник сортировки `sort_groups_by_size_desc`.
- `hashing.py` — вычисление хешсумм (`FileHasher` — абстракция, `HashlibFileHasher` — реализация; умеет считать хеш и всего файла, и только его префикса — один и тот же метод для обоих случаев, DRY).
- `hash_computation.py` — вычисление хешей для набора файлов (`HashComputationStrategy` / `ThreadPoolHashComputation`) — последовательно или в пуле потоков; сюда же подключается индикатор прогресса.
- `progress.py` — индикатор прогресса (`ProgressReporter` / `NullProgressReporter` / `SpinnerProgressReporter`).
- `scanning.py` — обход файловой системы (`FileScanner` / `RecursiveFileScanner`).
- `matching.py` — критерий "что считать дубликатом" (`DuplicateKeyStrategy` / `AttributeKeyStrategy`).
- `finder.py` — оркестрация трёхстадийного файлового поиска (`DuplicateFinder`), зависит только от абстракций выше (Dependency Inversion). `find_files()` отдаёт ещё и промежуточные данные (`FileScanResult`) для `DirectoryDuplicateFinder`.
- `directory_finder.py` — поиск директорий-полных-дубликатов (`DirectoryDuplicateFinder`) поверх уже посчитанных файловых хешей, без единого лишнего чтения с диска; `filter_subsumed_file_groups` убирает файловые группы, покрытые найденным дубликатом-директорией.
- `reporting.py` — форматирование результата (`ReportFormatter` / `TextReportFormatter` / `JsonReportFormatter`), с меткой типа записи (файл/директория).
- `utils.py` — общие мелкие хелперы: `human_readable_size`, а также `group_by` / `drop_singleton_groups` — переиспользуемый паттерн "сгруппировать и отбросить одиночные группы", на котором построены все три стадии фильтрации в `finder.py` (DRY).
- `storage.py` — сохранение результатов в локальные файлы (`ResultExporter` / `SqliteResultExporter` / `JsonResultExporter` / `DataFrameResultExporter` / `ExcelResultExporter` / `ResultPersistence`).
- `result_merge.py` — объединение результатов нового запуска с ранее сохранёнными по timestamp (`load_previous_rows` / `merge_with_previous`), для `--append-timestamp`.
- `cli.py` — точка сборки: разбор аргументов и связывание конкретных реализаций (единственное место, знающее обо всех классах сразу).

Каждый интерфейс (`FileHasher`, `FileScanner`, `DuplicateKeyStrategy`,
`HashComputationStrategy`, `ReportFormatter`) можно расширить новой
реализацией, не изменяя существующий код (Open/Closed) — например,
добавить хеширование через `xxhash`, другой обходчик директорий (с
игнор-листами), вычисление хешей через `multiprocessing` вместо потоков
или CSV-отчёт.
